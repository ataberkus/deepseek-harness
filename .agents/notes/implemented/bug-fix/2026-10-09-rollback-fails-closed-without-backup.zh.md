# Agent Note：工作区回滚在备份不可读时失败关闭

Status: implemented

[English](2026-10-09-rollback-fails-closed-without-backup.md) | 中文

## 问题

`workspace-checkpoint-local` 中的 `rollbackJournal` 先移除 cwd 下所有未排除的条目，再用 `.catch(() => undefined)` 构建备份目录的清单，清单缺失时直接返回。备份缺失或不可读时，cwd 被清空，没有任何内容被恢复，函数却正常返回。`restoreCheckpoint` 只在回滚抛出异常时调用 `markRecoveryRequired`，所以 Host 认为回滚已完成，并继续针对空工作区运行模型工作。

## 决策

`rollbackJournal` 先读取备份清单，读取失败时直接向上抛出。备份被读取并遍历完成之前不会移除任何工作区条目，因此失败时 cwd 保持失败恢复留下的状态。已有的回滚失败路径随后把工作区标记为 `recoveryRequired` 并重新抛出。成功路径按相同顺序执行相同的删除与复制。

回滚完成后现在也会移除日志文件，这与 `removeJournal` 契约原本的描述一致。回滚抛出异常时保留日志。已回滚尝试的暂存目录与备份目录会保留，直到下一次恢复同一检查点时将其移除。

## 考虑过的替代方案

**保留吞掉异常的写法，并在清单为 undefined 时标记需要恢复。** 删除仍发生在检查之前，工作区在失败被报告前就已被清空。

**先把备份复制到临时目录再交换。** 这样可以彻底消除删除与复制之间的窗口，但需要工作区的第二份完整副本，而且对备份不可读的情况没有改变，因为两种做法都在读取处失败。

## 后果

备份不可读时报告 `CHECKPOINT_CONTAINMENT` 或底层文件系统错误，并在恢复某个检查点之前阻止模型工作。第一次删除到最后一次复制之间的窗口仍然存在：该窗口内的复制错误会留下部分工作区，并同样标记需要恢复。

`restore` 会为被恢复的会话发出两次 `workspace-checkpoint/changed`：一次是清除 recovery 标记重写工作区各会话行时，一次是记录已应用检查点时。第一次覆盖共享该工作区的所有会话，第二次只覆盖被恢复的会话；观察者会重新读取 domain，所以对被恢复的会话来说多出的一次事件是冗余但无害的，保持不变。
